\section{Architektura Systemu}
\label{sec:Architektura_systemu}

Niniejszy rozdział przedstawia zaprojektowaną architekturę systemu, obejmującą wybrane komponenty, ich wzajemne powiązania oraz przesłanki kluczowych decyzji projektowych. Najbardziej rozbudowane funkcjonalności zostały opisane w odrębnych rozdziałach.

\subsection{Cele i ograniczenia projektowe}

Projektując system, kierowano się pięcioma celami:

\begin{enumerate}
  \item \textbf{Pełna automatyzacja} --- użytownik jedynie będzie używać \texttt{git push} lub uruchamiać aplikacje; walidacja, trening, ocena jakości i wdrożenie odbywają się bez interwencji.
  \item \textbf{Reprodukowalność} --- każda wersja modelu musi być powiązana z wersją kodu, wersją danych i zapisanymi metrykami.
  \item \textbf{Kontrola kosztów} --- projekt realizowany w ramach konta AWS Academy z budżetem 50~USD, dlatego zasoby uruchamiane są wyłącznie w momencie ich faktycznej potrzeby. 
  \item \textbf{Kontrola czasu} --- całkowity pipeline nie powinien przekraczać 4-godzinnego okna sesji laboratorium AWS. Szacowany czas samego treningu wynosił ok.~3~h.
  \item \textbf{Porównywalność} --- system musi być zbudowany w sposób umożliwiający zebranie wymieranych danych w celu porównania z podejściem manualnym.
\end{enumerate}

Dodatkowym ograniczeniem środowiska AWS Academy był zakres uprawnień przydzielonej roli laboratoryjnej, który nie umożliwiał bezpośredniej konfiguracji federacji tożsamości OIDC (ang. OpenID Connect, mechanizm federacyjnego uwierzytelniania) dla zewnętrznych systemów CI/CD, takich jak GitHub Actions. W ramach przyznanych uprawnień IAM (ang. Identity and Access Management, system zarządzania tożsamością i dostępem) mechanizm ten nie był dostępny do konfiguracji. Dozwolone było natomiast korzystanie z ról IAM przypisanych do instancji EC2.

W konsekwencji wykorzystano tymczasowe klucze sesyjne generowane przy każdym uruchomieniu środowiska laboratoryjnego. Klucze te były przechowywane jako zaszyfrowane sekrety repozytorium GitHub i wstrzykiwane do zmiennych środowiskowych workflow podczas jego wykonywania \cite{github_actions_docs}. Ze względu na czasowy charakter sesji laboratoryjnych (maksymalnie kilka godzin), sekrety były rotowane ręcznie przy każdym odnowieniu środowiska, co stanowiło akceptowalny kompromis w kontekście projektu badawczego (rysunek~\ref{fig:github-secrets}).

\subsection{Struktura repozytoriów}

Projekt korzysta z dwóch repozytoriów Git połączonych mechanizmem submodułów:

\begin{itemize}
  \item \textbf{Water-Meters-Segmentation-Automatization} --- repozytorium główne, zawiera kod ML, metadane danych treningowych śledzone przez DVC, workflow GitHub Actions, konfigurację Docker oraz skrypty pomocnicze. Obsłusuje wyzwalanie całego procesu CI/CD. 
  \item \textbf{DevOps-AI-Model-Automatization} --- repozytorium infrastruktury, dołączone jako submoduł pod ścieżką \texttt{devops/}. Zawiera moduły Terraform, chart Helm modelu ML, skrypty konfiguracyjne EC2.
  \item \textbf{Water-Meters-Segmentation} --- oryginalne repozytorium modelu U-Net. Służy wyłącznie jako punkt odniesienia maksymalnie wytrenowanego modelu (Dice~0,9275, IoU~0,8865).
\end{itemize}

Podział na dwa repozytoria wynika z odmiennej dynamiki zmian: kod ML oraz dane treningowe aktualizowane są często i wyzwalają automatyczne procesy CI/CD, natomiast definicja infrastruktury zmienia się rzadziej i jest modyfikowana w sposób kontrolowany. Zastosowanie mechanizmu submodułów pozwala powiązać konkretną wersję infrastruktury z konkretną wersją kodu aplikacji, zapewniając jednoznaczną zgodność środowiska wdrożeniowego.

Katalog \texttt{infrastructure/} w repozytorium głównym zawiera jedynie wartości konfiguracyjne specyficzne dla tej instalacji (\texttt{terraform.tfvars}, \texttt{helm-values.yaml}), które nadpisują szablony infrastruktury z submodułu. Szablony pozostają w repozytorium infrastruktury, natomiast parametryzacja wdrożenia wersjonowana jest razem z kodem aplikacji.

\subsubsection{Użytkownik (Data Scientist)}

Punktem wejścia do systemu jest lokalna maszyna użytkownika (Data Scientist). Interakcja z systemem ogranicza się do dwóch typów operacji:

\begin{itemize}
    \item dodawania nowych danych treningowych poprzez \texttt{git commit} i \texttt{git push},
    \item wykonywania predykcji poprzez uruchomienie skryptu \texttt{predicts.py}.
\end{itemize}

Zainstalowany hook Git \texttt{pre-push}~\cite{chacon2014pro_git} automatycznie wykrywa push zawierający dane treningowe i przekierowuje go na gałąź \texttt{data/TIMESTAMP}. Mechanizm ten inicjuje pipeline treningowy bez potrzeby wykonywania dodatkowych czynności przez użytkownika.

Użytkownik ma również dostęp do interfejsu MLflow oraz endpointu predykcyjnego modelu wdrożonego w chmurze.

\vspace{10px}

\subsubsection{Platforma kontroli wersji i automatyzacji (GitHub)}

  Centralnym punktem systemu jest platforma GitHub, łącząca kontrolę wersji kodu z automatyzacją procesu trenowania i wdrażania modelu.
  Repozytorium Git~\cite{chacon2014pro_git} przechowuje kod modelu, definicje workflow GitHub Actions, konfigurację wdrożenia (Helm) oraz pliki \texttt{.dvc}: lekkie metadane wskazujące na dane treningowe przechowywane w Amazon S3. Mechanizm DVC opisany jest szczegółowo w podrozdziale~\ref{subsec:dvc}.

\noindent\mbox{}\\\\ GitHub Actions~\cite{github_actions_docs} odpowiada za pełny cykl życia modelu (Workflow):

\begin{enumerate}
    \item wykrywa pojawienie się gałęzi danych,
    \item pobiera historyczne dane z S3,
    \item scala je z nowymi plikami,
    \item uruchamia walidację,
    \item startuje instancję EC2,
    \item przeprowadza trening,
    \item ocenia model przez bramkę jakości,
    \item w przypadku poprawy wdraża nową wersję i scala zmiany z gałęzią \texttt{main}.
\end{enumerate}

W trakcie wdrożenia obraz kontenera API budowany jest i publikowany do rejestru Amazon ECR, skąd następnie jest pobierany przez środowisko wykonawcze.

\subsubsection{Środowisko chmurowe AWS}

Granica AWS obejmuje zasoby infrastrukturalne tworzone deklaratywnie przy użyciu Terraform~\cite{hashicorp_terraform}. Kluczowe komponenty to:

\begin{itemize}
    \item instancja EC2 \texttt{t3.large} z przypisanym Elastic IP,
    \item dwa zasobniki Amazon S3: jeden dla danych DVC, drugi dla artefaktów MLflow,
    \item rejestr kontenerów Amazon ECR.
\end{itemize}

Zasobnik S3 dla DVC przechowuje wersjonowane dane treningowe, natomiast drugi zasobnik przeznaczony jest na artefakty MLflow (modele, metryki, pliki pośrednie). Rejestr ECR pełni rolę pośrednika między procesem budowania obrazu w GitHub Actions a jego uruchomieniem w środowisku produkcyjnym.

Instancja EC2 pełni podwójną rolę: podczas treningu hostuje serwer MLflow, natomiast na etapie wdrożenia działa jako self-hosted runner GitHub Actions zainstalowany jako usługa systemd, odpowiedzialna za budowanie obrazu Docker oraz aktualizację klastra k3s.

\subsubsection{Środowisko wykonawcze na EC2}

Na instancji EC2 działają dwa typy komponentów: usługi systemowe oraz workloady uruchamiane w klastrze k3s~\cite{k3s_docs}.

MLflow działa jako usługa systemowa (systemd) bezpośrednio na systemie operacyjnym instancji. Odpowiada za rejestrowanie eksperymentów, przechowywanie metryk oraz zarządzanie rejestrem modeli~\cite{mlflow_model_registry}. Artefakty zapisywane są w dedykowanym zasobniku S3.

Wewnątrz lekkiego klastra k3s uruchomione są:

\begin{itemize}
    \item API modelu (FastAPI + PyTorch),
    \item stos monitoringu (Prometheus + Grafana).
\end{itemize}

API modelu udostępnia endpoint \texttt{/predict}. Przy starcie kontenera model pobierany jest z rejestru MLflow w stadium Production, co rozdziela wersję obrazu kontenera od wersji samego modelu.

Prometheus zbiera metryki udostępniane przez API, a Grafana prezentuje je w postaci dashboardów. Konteneryzacja przy użyciu Docker~\cite{merkel2014docker} zapewnia powtarzalność środowiska uruchomieniowego niezależnie od cyklu start/stop instancji.
